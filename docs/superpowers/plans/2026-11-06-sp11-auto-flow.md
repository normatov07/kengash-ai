# SP11 Auto Flow Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An approved plan flows straight into tickets, then into the loop (asked, or at once with Auto mode), and `kengash` guarantees at most one live loop per project.

**Architecture:**
- A loop lease per conductor lives in `runtime/loops/<pid>.json`.
- Three new `ops` modules split the work:
  - `ops.conductors`: who is calling (moved out of `waiting`).
  - `ops.leases`: lease primitives under `locks/loops.lock`.
  - `ops.loops`: the claim, release and status use cases. Release counts runnable tickets through a side-effect-free `queue.compute` inside the same lock.
- `wait` claims, refuses and reports `queued` work.
- Skills hand over through `kengash skills show <name>`, rendered like an install.
- `loop_start: ask | auto` drives the end of the ticket skill, and the UI switches it.

**Tech Stack:** Python 3.12+, Pydantic, Typer, filelock, FastAPI, vanilla JS modules, pytest, node (static UI tests), headless Chrome over CDP.

**Spec:** `docs/superpowers/specs/2026-11-06-sp11-auto-flow-design.md`

## Global Constraints

- Exact output:
  - `loop claimed: <scope>`
  - `loop running: <agent> pid <pid> on <scope>, seen <age>`, where `<age>` is `just now`, or `N min ago` (whole minutes) once 60 s have passed
  - `this session holds the loop on <scope>`
  - `no loop running`
  - `loop_start: ask|auto`
  - `loop released: <scope>`
  - `no loop held here`
  - `not released: N runnable; run: kengash next`
  - a wait line `<id> queued loop n/max: <title>`

  `<scope>` is the slug, or `all projects`.
- Exit codes: `LoopBusy` exits 6; `not released` exits 1 (`UserError`).
- `LOOP_STALE_S = 3600`. A lease is live when its pid is alive, the pid's process name still equals `lease.command` (when that was recorded), and `now - seen < LOOP_STALE_S`.
- Events, journal only (`journal.append`, no store commit): `loop.started {project, pid, agent}` and `loop.ended {project, pid, agent, reason: released|taken_over|gone}`.
- Only `kengash` writes store and runtime files. Each `src/kengash_ai/<module>` change updates `docs/modules/<module>/README.md` in the same commit. Docs stay at or under 150 lines (specs and plans are exempt). The system spec changes before the code it governs (hard rule 1).
- Skills stay at or under 80 lines and 400 words, counted over the whole file with frontmatter (the lint's count). The caps never rise.
- UI: values go through `html`; every POST sends `X-Harness`; no `alert`, `confirm` or `prompt`; no horizontal scroll at 360 px.

## Review Focus

1. A session that ran `/kengash:loop`, was interrupted, and runs it again is never busy against itself: its own lease is refreshed and rescoped. Test `test_claim_by_the_same_conductor_refreshes_and_rescopes`, Task 2.
2. A recycled pid, alive but now another program, does not hold a loop. Test `test_a_reused_pid_is_not_live`, Task 2.
3. Planning project A while a loop runs on project B starts a loop for A. Test `test_claims_on_different_projects_coexist`, Task 2.
4. A blocked ticket's add is not `queued`; the merge that unblocks it is. Test `test_wait_reports_queued_for_ready_adds_and_unblocks_only`, Task 4.
5. A loop skill installed before SP11, which never claims, still holds a lease while it waits, and a second conductor's `wait` exits 6. Tests `test_wait_claims_for_a_detected_agent` and `test_wait_refuses_under_another_conductors_lease`, Task 4.

  - `overlaps(a: str | None, b: str | None) -> bool`
